Схема одинаковая: открываешь сессию на модели «для плана», получаешь план,
проверяешь глазами, переключаешься `/model` на модель «для кода», говоришь «делай».

Общий хвост, дописывать в конец **каждого** промта:

> Сначала выдай план: какие файлы трогаешь, какие создаёшь, какие миграции, какие
> тесты. Код не пиши, пока я не скажу «делай». После реализации прогони скрипты

## Блок 0 — Поллинг Авито

**План: Opus 5. Код: Sonnet 5.** Опус нужен, потому что тут разбор чужого API
и решение про холодный старт, а не набор кода.

```
Проект ai_seller_agent, ИИ-ассистент для мессенджера Авито. Python 3.12,
FastAPI, SQLAlchemy 2.x async, Alembic, asyncpg, Redis, деплой на Railway.

Проблема: Авито не доставляет вебхуки по объявлениям банного комплекса.
Подписка активна, эндпоинт живой, ручной POST на вебхук отрабатывает конвейер
целиком. Событий по нужным объявлениям нет ни одного. Переподписка помогала
один раз и ненадолго. Поддержка не вариант по срокам.

Задача: сделать поллинг как основной канал получения сообщений, вебхук
оставить как второй канал.

Требования:
1. Новый модуль app/avito/poller.py. Раз в 60 секунд GET
   /messenger/v2/accounts/{user_id}/chats с пагинацией по всем чатам аккаунта.
   Сравнение last_message.created с сохранённым курсором по чату. Где новее —
   GET /messenger/v3/accounts/{user_id}/chats/{chat_id}/messages/.
2. Курсоры хранить в Postgres, новая таблица chat_cursor + миграция Alembic.
   Не в файле и не в YAML: Railway эфемерна, файл не переживёт деплой.
3. Сообщения нормализовать в ТОТ ЖЕ внутренний event, что приходит из вебхука,
   и подавать в существующий конвейер входящих. Не дублировать логику дедупа,
   debounce, отсечения эха и сборки истории — переиспользовать.
4. Дедуп по message_id в Redis должен гарантировать, что вебхук и поллер,
   работая одновременно, не приведут к двойному ответу. Проверь, что текущий
   ключ дедупа это обеспечивает, если нет — почини.
5. Холодный старт. При первом проходе поллер увидит всю историю аккаунта.
   Переменная POLLER_BACKFILL_HOURS (дефолт 72): автоответ только там, где
   последнее сообщение входящее и свежее указанного окна. Все остальные чаты
   помечаются как seen без единого исходящего и попадают списком в /admin/dialogs
   с отдельной ручной кнопкой «обработать». Реанимация старых чатов не должна
   происходить сама.
6. item_id из API Авито приходит числом, в коде везде строка. Приводить к строке
   на границе, иначе сравнения молча не сработают — на этом уже горели.
7. Переподписка на вебхук по расписанию раз в сутки, в тот же планировщик.
8. Логировать через существующий форматтер с extra — он уже настроен.

Не трогай: движок цен, движок уступок, системный промт, Telegram-бот.
```

## Блок 1 — Область действия по объявлениям

**План и код: Sonnet 5.** Механика, архитектурных развилок нет.

```
Проект ai_seller_agent. Сейчас область действия агента задана чёрным списком
объявлений: пять зашитых в код id, всё остальное проходит. Нужно, чтобы агент
автоматически работал во всех объявлениях комплекса про баню и смежные зоны,
включая объявления, созданные после запуска агента, без ручного ведения списка.

Задача:
1. Таблица item_scope в Postgres + миграция Alembic. Поля: item_id (строка),
   title, decision (allow|deny), reason, updated_at.
2. Раз в час фоновая задача тянет все объявления аккаунта существующим
   scripts/export_listings и классифицирует по заголовку:
   allow, если матчится баня|банный|парная|сауна|чан|купель|купол|шатёр|юрта|
   гриль|беседка;
   deny, если матчится вакансия|продам|аренда бизнеса|квартира|студия|глэмпинг.
3. Жёсткий deny поверх любой классификации — пять текущих зашитых id, в первую
   очередь 8172444564 (квартира). Deny всегда выигрывает у allow.
4. Неизвестный item_id, которого нет в таблице: синхронно догрузить карточку
   объявления и решить на месте. Если запрос упал — allow, при условии что
   заголовок не матчит deny-слова.
5. Решение принимается в существующей единой точке фильтрации исходящих,
   через которую идут все четыре пути (ответ агента, отложенные касания, ответ
   на изображение, таймаут уступки). Новых точек фильтрации не создавать.
6. Тест: deny-список приоритетнее allow-классификации при любом заголовке.

После реализации прогони классификацию вживую и покажи таблицей, какие
объявления аккаунта получили allow, а какие deny.
```

## Блок 3 — Перехват менеджером

**План и код: Sonnet 5.** Маленький блок, но трогает исходящие, Haiku тут не надо.

```
Проект ai_seller_agent. Сейчас флаг is_human_takeover на чате глушит агента
навсегда. Заказчик хочет, чтобы агент работал во всех чатах по объявлениям про
баню независимо от того, отвечал ли там раньше живой менеджер.

Задача:
1. Переменная TAKEOVER_MODE со значениями off|cooldown|permanent, дефолт cooldown.
   cooldown: если исходящее сообщение от живого менеджера в чате было менее
   TAKEOVER_COOLDOWN_MINUTES назад (дефолт 15) — агент молчит, после окна
   возвращается сам.
   permanent: текущее поведение. off: флаг игнорируется.
2. Отличать сообщение менеджера от сообщения агента. Проверь, как сейчас
   работает отсечение эха, и переиспользуй тот же признак.
3. Команда /hold <chat_id> и /unhold <chat_id> в Telegram-боте для явной ручной
   паузы без ограничения по времени. Это отдельный флаг, он не сбрасывается
   по кулдауну.
4. Решение принимается в той же единой точке фильтрации исходящих.
5. Тесты на все три режима.

Отдельно: в БД есть три чата по объявлению квартиры с takeover, там реальные
люди. Выведи их chat_id и последние 10 сообщений каждого, я разберу руками.
Объявление квартиры остаётся в жёстком deny.
```

## Блок 2 — Снятие всех эскалаций кроме скидок

**План: Opus 5. Код: Sonnet 5.** Тут поведенческие ветки агента и системный
промт — на Sonnet планировать не стоит.

```
Проект ai_seller_agent. Цель: агент работает полностью автономно и запрашивает
человека ТОЛЬКО при ценовой уступке. Сейчас MODERATION_MODE=concessions_only,
но эскалация зашита ещё в нескольких местах.

Шаг 1. Сделай полную инвентаризацию: найди все точки кода, откуда агент уходит
в эскалацию или в молчание с ожиданием человека. Выдай таблицей: файл, строка,
условие, что происходит сейчас. Ничего не меняй, пока не покажешь таблицу.

Шаг 2. По известным мне точкам нужное поведение:
- DisputedValue со значением null: я добью цифры у заказчика, но добавь на старте
  явный отчёт, какие поля до сих пор null и в каких сценариях они всплывут.
- check_availability возвращает unknown по любой зоне: не эскалировать. Пробовать
  постановку брони — YCLIENTS отдаст конфликт, если слот занят, и тогда агент
  сам предлагает соседние слоты. Идемпотентность и повторная проверка слота уже
  реализованы, переиспользовать.
- Блокирующие вопросы 12.1 и 12.2 в базе знаний: убрать блокирующий характер,
  они видны в логе при старте.
- Падение LLM: убрать фолбэк на Anthropic, ANTHROPIC_API_KEY сейчас заглушка
  sk-ant-xxxxx и при переключении всё упадёт. Фолбэк на deepseek-v4-flash.
- resolve_date: расширить на «в следующую субботу», «на выходных», «через
  неделю», «в ближайшие выходные». Это уточнение у клиента, а не эскалация,
  но людей раздражает.

Шаг 3. Защита от регресса. Напиши тест, который разбором AST проверяет, что
функция эскалации вызывается только из quote_gate. По образцу существующего
теста, который запрещает float в движке цен.

Шаг 4. Обнови системный промт: агент не обещает «уточню и вернусь», не ссылается
на менеджера, не предлагает перезвонить. Если данных не хватает — задаёт вопрос
клиенту или предлагает бронь под подтверждение.

Не трогай движок уступок и храповик в quote_gate — модерация скидок остаётся.

**План: Sonnet 5. Код: Haiku 4.5.** Чистая обвязка.

```
Проект ai_seller_agent. Агент переводится в полностью автономный режим, за ним
никто не смотрит ежедневно. Нужны предохранители и наблюдаемость.

1. Глобальный лимит исходящих: не более AGENT_MAX_OUTBOUND_PER_DAY (дефолт 300)
   сообщений в сутки по московскому времени. При достижении — полная остановка

4. Ежедневный дайджест в Telegram в 10:00 МСК: новых чатов, отправлено ответов,
   поставлено броней, запрошено уступок, сколько отклонено, ошибки за сутки.
5. LOG_ALL_INBOUND перевести в false по умолчанию.
6. Проверь, что все новые таблицы из предыдущих блоков покрыты миграциями
   Alembic и миграции применяются в entrypoint.sh до старта приложения.

   есть — прогони и покажи вывод.

## Критерий сдачи

- 48 часов в проде без единой эскалации, кроме ценовых
- получены и обработаны сообщения минимум по трём разным объявлениям бань
- хотя бы одна бронь поставлена из чата, начатого до запуска агента
- в базе знаний нет ни одной DisputedValue со значением null
- дайджест в Telegram приходит два дня подряд
