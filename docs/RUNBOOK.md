# RUNBOOK — эксплуатация агента «ПарМангал»

Документ для дежурного. Всё, что здесь описано, выполняется без чтения кода.

## Аварийный рубильник

Агент пишет клиентам ерунду / клиент жалуется / непонятно что происходит:

```bash
```
В Telegram: **/pause** — агент немедленно замолкает во всех чатах, диалоги
переходят к операторам. Обратно — **/resume**.

Если Telegram недоступен:

```bash
docker compose -f docker-compose.prod.yml stop app
```

Вебхуки Авито в это время будут получать ошибку и повторяться — сообщения не
потеряются, но накопятся.

## Типовые ситуации

### Агент молчит: сообщения вообще не доходят

Сначала выяснить, доходят ли они до конвейера. Одна строка на КАЖДОЕ
входящее пишется до всех проверок:

```
poller: проход завершён — чатов 1100, с новыми 2, подано сообщений 3, ...
pipeline: входящее source=poller chat_id=u2i-... item_id='7980589876'(str) ...
```

- **Нет строки `poller: проход завершён`** — поллер не работает. Смотреть
  `POLLER_ENABLED`, а в логе — `poller: проход упал целиком`. Если строка
  `проход пропущен — опрашивает другая реплика` повторяется постоянно,
  значит захват в Redis завис: снять ключ `avito:poller:lock`.
- **Проход есть, `подано сообщений 0`** — смотреть `причины пропуска` в той
  же строке. `not_our_listing` означает чат по чужому объявлению,
  `up_to_date` — новых сообщений правда нет. Холодного старта как отдельной
  причины больше нет — поллер читает чат без курсора той же веткой, что и
  любой другой (см. app/avito/poller.py); отвечать или нет решает
  `AGENT_MIN_INBOUND_TS` в конвейере, см. следующий пункт.
- **`pipeline: входящее старше AGENT_MIN_INBOUND_TS — исходящее не
  порождается`** — штатно, если порог настроен и сообщение старше него.
  Сообщение записано в историю диалога, ответа не будет ни в каком виде —
  это не баг, это и есть защита от инцидента 2026-08-28 (65 сообщений в
  старые чаты). Поднимать порог не нужно — снимается только сменой
  `AGENT_MIN_INBOUND_TS`, осознанно.
- **`список объявлений аккаунта недоступен и снимка нет — проход отменён`** —
  не отвечает `GET /core/v1/items`. Проход намеренно не делает ничего:
  проверить принадлежность чата нечем, а отвечать вслепую хуже, чем молчать.
- **Строка `pipeline: входящее` есть, ответа нет** — дальше уже не про канал,
  см. остальные разделы: фильтр объявлений, лимит ответов, takeover.

### Агент ответил дважды на одно сообщение

Значит развалился дедуп между вебхуком и поллером. Ключ
`avito:seen_message:{message_id}` работает только пока Авито называет одно
сообщение одним идентификатором в обоих каналах. Проверить:

```bash
python -m scripts.poll_once --check-ids
```

Если вердикт «НЕ СОВПАЛИ» — нужен составной ключ, править
`app/channels/inbound_dedup.py`. Второй возможной причиной остаётся пустой
`REDIS_URL`: без Redis заявка не ставится вовсе, и от повторного ответа
защищает только уникальный индекс в `messages` — а сообщения без текста
(фото) он не покрывает.

### Поллер пропустил хвост переписки

```
poller: упёрлись в потолок страниц (10 x 20), часть истории чата не прочитана
```

Бывает после долгого простоя. Поднять `POLLER_MAX_MESSAGE_PAGES` и дождаться
следующего прохода — курсор не двигался, сообщения не потеряны.

### Протух токен Авито

Симптом: в логах 401 подряд, `avito token refreshed` не появляется.

```bash
python -m scripts.rotate_avito_keys --check
```

Если ключи рабочие — сбросить кеш токена:

```bash
docker compose -f docker-compose.prod.yml exec redis redis-cli DEL avito:access_token
```

Если не рабочие — сменить по инструкции: `python -m scripts.rotate_avito_keys --new-id ... --new-secret ...`

### Вебхук перестал приходить

Проверить подписку:

```bash
python -m scripts.register_webhook --list
```

Перерегистрировать (секрет подставится сам из `.env`):

```bash
python -m scripts.register_webhook https://parmangal.example.ru
```

Если сменили `AVITO_WEBHOOK_SECRET`, старая подписка перестанет работать —
адрес изменился. Обязательно перерегистрировать.

### Вебхук приходит, но агент не отвечает

Вебхук отвечает `200` всегда — даже когда обработка потом падает (иначе Авито
начнёт ретраить). Поэтому «200 в логах» ещё не значит, что ответ сформирован.
Идти по цепочке `app/pipeline.py` сверху вниз, в логах искать `parmangal.pipeline`:

| строка в логе | что произошло | что делать |
|---|---|---|
| ничего вообще | `handler` не подключён | в логе старта должно быть `incoming pipeline: wired to the Avito webhook` |
| `webhook duplicate dropped` | Redis уже видел этот `message_id` | норма при ретрае Авито |
| `duplicate incoming message dropped by the unique index` | Redis сбросился, поймал индекс в БД | норма, второй рубеж сработал |
| `message without text` | картинка/системное событие | ожидаемо, агент такие не обрабатывает |
| `chat is with a human` | оператор забрал чат | вернуть кнопкой «Вернуть ИИ» |
| `takeover during debounce window` | оператор забрал чат за те секунды, что клиент дописывал | то же самое |
| `agent stays silent` + `reason` | сработал один из стопоров `should_agent_reply` | смотреть reason: пауза, лимит ответов, ИИ выключен для чата |
| `agent produced no reply` | классификатор счёл входящее спамом | проверить текст клиента в `/admin/dialogs` |
| `agent turn failed` | упал ход агента (провайдер, БД) | traceback тут же в логе |
| `sending to Avito failed` | ответ есть, отправка не прошла | сообщение сохранено со статусом `failed`, клиент его не получил |

Ответ не появляется мгновенно и это нормально: сообщения склеиваются окном
`DEBOUNCE_WINDOW_SECONDS` (по умолчанию 10 с), а вне `DRY_RUN` добавляется ещё
пауза 3–8 с, чтобы ответ не выглядел автоматическим.

В `DRY_RUN` ответ клиенту не уходит вообще — он встаёт в очередь модерации.
Если карточка не пришла в Telegram, ответ всё равно там: `/admin/dialogs`.

### Превышен дневной лимит расхода

Агент уходит на паузу сам, в Telegram приходит алерт. Проверить расход:
`/admin/costs`. Поднять лимит — `DAILY_COST_LIMIT_RUB` в `.env` и перезапуск.

### Агент называет неверную цену

1. Немедленно **/pause**.
2. Открыть `/admin/readiness` — зона, вероятно, помечена `ready_for_pricing: нет`.
3. Проверить, не появилось ли в `catalog.yaml` поле с `value`, которое должно
   быть `disputed`. Кардинальное правило: спорное поле возвращает `blocked`,
   а не цифру.
4. Прогнать `python -m scripts.replay` — сравнение с эталоном покажет регрессию.

### Агент постоянно эскалирует «занятость неизвестна» по YCLIENTS

Симптом: даже по датам, где точно должно быть известно, ассистент отвечает
«уточню у менеджера», а не называет свободные слоты.

1. В логах ищите `yclients: интеграция не подключена филиалом` — это САМАЯ
   частая причина и не баг кода: зайти в личный кабинет YCLIENTS и нажать
   «Подключить» у интеграции. Формально верные токены без этого шага всё
   равно получат отказ в доступе.
2. Если такой строки нет, а есть просто `yclients request failed: ...` —
   сетевая проблема или сбой самого YCLIENTS, разбираться по типу исключения
   в логе.
3. Зона называется «не заведена в системе бронирования»? Каталог услуг у
   заказчика наполняется постепенно — это ожидаемое состояние, а не ошибка,
   см. `/admin/booking` (`app.booking.mapping.coverage_report`) для списка
   заведённых/незаведённых зон.
4. `SPEC_VERIFIED` в `app/booking/yclients_endpoints.py` должен быть `True`
   на этом этапе проекта — если кто-то откатил его на `False`, все запросы
   к YCLIENTS блокируются намеренно, до этой строки код даже не доходит.

### Отложенные касания не уходят

Симптом: клиент назвал цену, молчит больше 30 минут, второе касание («вы
где-то затерялись?») не приходит.

1. В логах должна быть строка `touch scheduler: started` на старте процесса
   и `touch sent` при каждой реальной отправке. Если строки `started` нет —
   воркер не поднялся вообще, смотреть трейс сразу после неё в логах.
2. `touch scheduler: pass failed` в логах — воркер жив, но каждый проход
   падает (обычно недоступна БД или Авито). Один сбитый проход не страшен,
   воркер сам повторит через `TOUCH_SCHEDULER_INTERVAL_SECONDS`; если строка
   повторяется постоянно — чинить первопричину (см. «Протух токен Авито»
   выше, если дело в Авито).
3. Ночью (не в окне `working_window`, по умолчанию 9:00–23:00) касания
   намеренно не уходят — это ожидаемое поведение, не баг. Просроченный
   ночью диалог никуда не теряется: состояние в БД не трогается, и первый
   же дневной проход воркера его отправит.
4. Если DRY_RUN=true, а карточка в Telegram не появилась — проверить
   `TELEGRAM_OPS_CHAT_ID`: без него касание всё равно встаёт в очередь на
   одобрение (видно в `/admin/dialogs`), просто оператор не получит
   уведомление сам.
5. Таймер заводится только ПОСЛЕ названной цены (`base_price_quoted`).
   Диалог, где до цены не дошло, касаний не получает вообще — это
   регламент, а не сбой.

### Клиенту пришло «Вы где-то затерялись?», хотя он только что ответил

Так быть не должно: конвейер сбрасывает таймер на каждом входящем сообщении
клиента (`reset_timer_on_reply`), причём до всех проверок — даже когда чат
забрал оператор. В логах на каждое такое сообщение обязана быть строка
`pipeline: touch timer reset on client reply`.

Если её нет, а касание ушло — проверить в этом порядке:

1. Дошло ли само сообщение: строка `webhook duplicate dropped` означает, что
   Авито прислал ретрай уже обработанного сообщения — такой дубль намеренно
   НЕ сбрасывает таймер (иначе ретраи бесконечно отодвигали бы напоминание).
2. `next_touch_due_at` в таблице `dialog_states` для этого `chat_id`: после
   ответа клиента там должен быть `NULL`.
3. Конвейер и воркер пишут в одни и те же колонки `dialog_states`. Если
   значение не `NULL` — сбой был на записи, смотреть `parmangal.pipeline`
   в логах в момент прихода сообщения.

### Восстановление базы из дампа

**На VPS** (docker-compose.prod.yml): дампы лежат в `./dumps`, хранятся 14 дней,
их пишет отдельный сервис `backup` в самом compose-файле.

```bash
gunzip -c dumps/2026-08-20.sql.gz | docker compose -f docker-compose.prod.yml exec -T postgres psql -U parmangal parmangal
```

**На Railway** свой cron-дамп не запускается намеренно — контейнер там может
перезапуститься в любой момент (не только при сбое, но и при деплое), и
процесс вида «раз в сутки писать дамп на диск контейнера» этого не переживёт:
диск эфемерный, накопленные дампы пропадут вместе с перезапуском. Резервное
копирование Postgres на Railway — забота самой платформы (Managed Postgres
делает снепшоты сам); восстановление — через её интерфейс/CLI, не через этот
раздел. Подробности — docs/RAILWAY_SETUP.md.

## Что агент не делает никогда

Если увидели такое в переписке — это баг, заводите issue и ставьте на паузу:

- назвал реквизиты, номер карты, телефон получателя или название банка;
- подтвердил бронь без слов «менеджер свяжется и подтвердит»;
- назвал сумму по зоне, помеченной в `/admin/readiness` как неготовая;
- предложил скидку без записи в журнале `/admin/concessions`.

## Метрики и алерты

`/metrics` для Prometheus (наружу закрыт, доступен внутри сети).

Алерты в Telegram настроены на:
- ошибки Авито и Anthropic API;
- превышение дневного лимита расхода (плюс автопауза);
- долю уступок выше порога;
- необработанные исключения.

## Критерии выключения модерации

Не выключать DRY_RUN, пока не выполнены все четыре:

- ≥90% ответов одобряются без правок три дня подряд;
- ноль неверных цен за неделю;
- стоимость диалога < 15 ₽;
- доля эскалаций < 20%.

Выключать **по зонам**, начиная с самых простых. Шатёр и корпоративы оставить
на операторе дольше всех.
