# Чек-лист запуска

Порядок действий перед включением DRY_RUN на живой трафик, и что делать, если
что-то пошло не так. Кто выполняет каждый шаг — отмечено в скобках.

## Перед первым включением

1. **Ключи в `.env`** (мы). Скопировать `.env.example` → `.env`, заполнить:
   `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET`, `AVITO_USER_ID`,
   `AVITO_WEBHOOK_SECRET` (сгенерировать: `python -c "import secrets; print(secrets.token_urlsafe(32))"`),
   `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OPS_CHAT_ID`,
   `TELEGRAM_ALLOWED_USERS`.
   `DRY_RUN=true` — оставить как есть, это защитный режим по умолчанию.

2. **Прогнать всю тестовую сюиту** (мы):
   ```bash
   python -m pytest tests/ -q
   ```
   Должно быть 100% зелёных. Если хоть один тест красный — запуск откладывается
   до починки, без исключений.

3. **Проверить готовность зон** (мы):
   ```bash
   python -m app.kb.loader
   ```
   Ожидаем: все 10 зон — `yes` в обеих колонках. Если не так — что-то откатилось
   в базе знаний, нужно разбираться прежде чем продолжать.

4. **Прогнать харнесс на реальной модели** (мы, нужен `ANTHROPIC_API_KEY`):
   ```bash
   ANTHROPIC_API_KEY=... python -m scripts.replay --baseline
   ```
   Смотрим долю чистых ходов (жёсткие проверки — цены, реквизиты, длина
   сообщений) и средний балл судьи по тону. Если балл заметно ниже, чем у
   живых менеджеров — правим секцию тона в `app/agent/prompts.py` и гоняем
   заново, пока не сравняется или не обгонит. Это единственная метрика, ради
   которой стоит итерировать перед показом результата вам.

5. **Регистрация вебхука** (мы):
   ```bash
   python -m scripts.register_webhook https://<ваш домен>
   ```
   Домен должен быть на HTTPS — без этого Авито не пришлёт ни одного
   сообщения.

6. **Проверить `/health`** (мы): должен отвечать `{"status": "ok"}`.

## Первая неделя — DRY_RUN на живом трафике

7. Агент отвечает на реальные сообщения, но **ни одно не уходит клиенту без
   вашего одобрения** в Telegram — под каждым ответом кнопка «Одобрить и
   отправить» и «Отклонить».

8. Это заодно лучший способ добрать недостающие ответы: на живых вопросах
   сразу видно, чего в базе знаний не хватает. Открытые пункты — в
   `questions_for_client.md`.

9. Раз в день смотрим `/admin/costs` (расход на модели) и `/admin/concessions`
   (журнал скидок — каждая скидка обязана быть видна отдельной строкой).

## Когда выключать модерацию

Не раньше, чем выполнены **все четыре** условия одновременно:

- ≥ 90% ответов одобряются без правок **три дня подряд**;
- ноль неверных цен за неделю (сверяем по `/admin/dialogs`);
- стоимость одного диалога < 15 ₽ (`/admin/costs`);
- доля эскалаций < 20% от всех диалогов.

**Рубильников два, и порядок важен.** `DRY_RUN` — старший: пока он включён,
на одобрение уходит всё. Сняли его — дальше решает `MODERATION_MODE`
(`/moderation` в боте): `all` — держать на одобрении всё, `concessions_only`
(**по умолчанию**) — только ценовые уступки, `off` — полная автономия.

Значит после `DRY_RUN=false` с дефолтной настройкой бóльшая часть ответов
пойдёт клиентам без вашей кнопки. Ослабляйте по одному шагу:
`DRY_RUN=false` + `/moderation all` → пожили → `/moderation concessions_only`.

По зонам выключать нельзя: оба рубильника глобальные, на все чаты сразу.
Отдельной строгости для шатра, крупных компаний и домика — там самые большие
суммы и ступень уступки на 5 500 ₽ — в системе нет; если она нужна, это
отдельная работа, а не настройка.

## Если что-то пошло не так

**Немедленная остановка:** в Telegram команда `/pause` — агент перестаёт
отвечать во всех чатах, все диалоги переходят на менеджеров. Возврат —
`/resume`.

Дальше — по `docs/RUNBOOK.md`: там расписан разбор для каждой типовой
ситуации (протухший токен, вебхук перестал приходить, превышен дневной
лимит расхода, агент назвал неверную цену, откат релиза).

## LLM-провайдер: Anthropic или DeepSeek (промт №12)

Заказчик может подключить свой ключ DeepSeek — их токены, их расходы.
Технически это подмена `base_url`/ключа/имени модели: DeepSeek отдаёт
Anthropic-совместимые ответы на `https://api.deepseek.com/anthropic`,
поэтому весь остальной код (цикл ходов, инструменты, движок цены) работает
без изменений — см. `docs/PROVIDER_COMPARISON.md` за подробностями и
цифрами сравнения.

**Переключение:**

- `LLM_PROVIDER=anthropic|deepseek` в `.env` + перезапуск процесса —
  пересборка образа не нужна.
- Из Telegram, без перезапуска: `/provider` — показать текущий и резервный,
  `/provider deepseek` — переключить.
- `LLM_FALLBACK_PROVIDER` — резервный провайдер, включается сам после
  `LLM_FALLBACK_AFTER_ERRORS` (по умолчанию 3) ошибок основного подряд.
  Обратно на основного — только вручную, автовозврата нет: если DeepSeek
  полежал и ожил, агент не должен молча прыгать обратно на резерв без ведома
  оператора.
- `/admin/costs` показывает расход в разбивке по провайдеру и по модели.

**Перед тем, как включить DeepSeek на реальный трафик:**

1. Прогнать `python -m scripts.compare_providers` с обоими ключами
   (`ANTHROPIC_API_KEY` и `DEEPSEEK_API_KEY`) и показать заказчику
   `docs/PROVIDER_COMPARISON.md` — решение по цифрам, а не по мнениям.
2. Известное архитектурное отличие: у DeepSeek нет reального strict mode на
   Anthropic-совместимом пути (см. отчёт) — правильность вызова инструментов
   у него ниже гарантирована схемой и выше зависит от последнего рубежа
   (`app/agent/loop.py`) и валидации аргументов внутри инструментов. Если
   сравнительный прогон покажет много кривых вызовов у DeepSeek — это повод
   не включать его на не-модерируемый трафик, а не повод чинить незаметно.
3. `DEEPSEEK_ENABLE_THINKING` оставлять `false`, пока не появится измеренная
   причина включать — с ним растут и стоимость, и задержка хода.

## Контроль версий базы знаний

`app/kb/catalog.yaml` — единственный источник цен для агента. Любое ручное
изменение цифры в нём должно тут же сопровождаться:

- пометкой `resolved_from:` — кто и на основании чего разрешил значение;
- прогоном `python -m pytest tests/test_kb.py tests/test_pricing.py -q`.

Спорное поле — это `value: null` плюс блок `disputed:` с номером вопроса.
Никогда не подставляйте цифру «на глаз», даже временно — движок для
неразрешённых полей и так корректно уходит к менеджеру, это ожидаемое и
безопасное поведение, а не баг.

### Что правится из Telegram, а что нет

Редактор в боте оператора умеет ровно 11 полей (`app/kb/editable.py`): цены
зон по будням/выходным, суточные, минимальные часы, вместимость, цена пакета
«весь день», границы рабочего окна и список праздников. Правка любого из них
доезжает до расчёта без рестарта.

**Всё остальное в YAML редактор не видит, и часть этого на поведение не
влияет вообще — даже если поправить файл руками.** Так устроены:

- `payment.yaml` — поля `ai_may_send_payment_link`, `ai_may_send_bank_details`,
  `ai_may_send_phone_number`, `link_type`, `refund_rule`,
  `no_credentials_policy`. Они грузятся и валидируются, но кодом не читаются:
  запрет на реквизиты держится текстом системного промта
  (`app/agent/prompts.py`, правило 5), а правило возврата доезжает до агента
  потому, что продублировано в `catalog.yaml → knowledge`. Поставить
  `ai_may_send_bank_details: true` — агент всё равно не станет диктовать
  реквизиты; поставить `false` там, где сейчас `true`, — ничего не запретит.
  Единственное поле файла, которое реально управляет поведением, —
  `handoff_on_payment_step` (передача этапа оплаты оператору, проверяется в
  коде перед вызовом YCLIENTS).
- `catalog.yaml → escalation_topics` (животные, стол для гостей юрты, своя
  палатка). Тоже мёртвая декларация: правило «цену не называть, звать
  человека» живёт в промте (правило 6a), и правка YAML его не изменит.

Менять поведение в этих двух местах — значит править
`app/agent/prompts.py` и выкатывать, а не редактировать базу знаний.
